Laboratory 5 instruction part 2 - MLflow¶

Introduction¶

In machine learning development, one of the most challenging aspects is maintaining reproducibility. This issue is particularly relevant to the experimental phase, when a lot of small, but influential code changes are constantly introduced.

After extensive experimentation with different model architectures, hyperparameters, and preprocessing techniques, researchers often find themselves unable to recreate their best-performing models because critical configuration details were not properly recorded.

MLflow is an open-source platform that addresses this challenge by providing systematic experiment tracking throughout the machine learning lifecycle. It automatically captures configurations, metrics, and artifacts from each model training run, transforming ad-hoc model development into a structured, reproducible process. In this lab, we will use MLflow 3 to track experiments for both traditional machine learning and deep learning workflows.

We will cover:

  • MLflow tracking server configuration and deployment for experiment management
  • automatic logging for scikit-learn experiments
  • linking experiments with DVC data versions
  • manual logging for PyTorch deep learning workflows, with a modern tabular deep learning model
  • systematic hyperparameter optimization with Optuna
  • Model Registry, versioning and promoting models with aliases

We continue in the same repository and virtual environment as in the DVC part.

MLflow tracking server¶

MLflow Tracking is the main component of MLflow, responsible for capturing, storing, and presenting metrics, logs, and other tracking data. MLflow is based on a client-server architecture, where the central MLflow server can serve potentially whole teams of data scientists. You can also simply run it as a local server from the commandline, as we will now.

You have two options for running MLflow: a simple local server, or a Docker container, which is closer to a production-like setup.

Local server¶

Open an additional terminal (or split the current one) and start the MLflow tracking server:

mlflow server \
  --backend-store-uri sqlite:///mlflow.db \
  --artifacts-destination ./mlflow-artifacts \
  --host 127.0.0.1 \
  --port 5001

Keep this terminal window open. The MLflow server will continue running and be accessible at http://localhost:5001.

Docker server¶

Create a docker-compose.yml file:

services:
  mlflow:
    image: ghcr.io/mlflow/mlflow:v3.18.0
    container_name: mlflow-server
    ports:
      - "127.0.0.1:5001:5000"
    volumes:
      - ./mlflow-data:/mlflow
    command:
      - mlflow
      - server
      - --backend-store-uri
      - sqlite:////mlflow/mlflow.db
      - --artifacts-destination
      - /mlflow/artifacts
      - --host
      - 0.0.0.0
      - --port
      - "5000"
    restart: unless-stopped

Keep the image tag equal to your MLflow client version, which you can check with mlflow --version. Mismatched client and server versions can cause hard to debug errors.

Start MLflow with Docker:

mkdir -p mlflow-data
docker compose up -d

Check if it's running, and optionally view the logs:

docker compose ps
docker compose logs -f mlflow

Note that on Linux, including WSL, the container writes to mlflow-data/ as root, so the files there are owned by root and you need sudo rm -rf mlflow-data to delete them later. Docker Desktop on macOS maps them to your user, so it's not an issue there.

Both setups use --artifacts-destination, so the server stores artifacts and the client sends them over HTTP. With --default-artifact-root, the client would instead write artifacts directly to that path on its own filesystem, which breaks as soon as the server runs in a container or on another machine.

Note that since MLflow 3.5, the server protects itself against DNS rebinding and by default only accepts requests addressed to localhost. This is fine for us, but if you deploy MLflow for a team, you need to configure --allowed-hosts and --cors-allowed-origins.

MLflow creates local files that should not be committed to Git. Add these lines to your .gitignore:

# MLflow
mlflow.db
mlflow-artifacts/
mlflow-data/
mlruns/

These files contain experiment data and artifacts that are specific to your local machine. In production, you would use a remote tracking server and artifact storage (like S3).

Training on such targets is possible, but very large target values easily risk overflow, particularly when a loss function like mean squared error is used. We will use the log-transform to transform this distribution, as it's near-exponential, so it should bring it closer to normal, and also greatly reduce the values range.

def make_pipeline(model) -> Pipeline:
    # train on log-prices, return predictions in dollars
    regressor = TransformedTargetRegressor(
        regressor=model, func=np.log1p, inverse_func=np.expm1
    )
    return Pipeline(
        [("preprocessing", clone(column_transformer)), ("model", regressor)]
    )

Autologging patches every fit() call, including the ones made internally by cross_val_score(). If we ran cross-validation inside a run, MLflow would log 5 additional fits and models into it, and overwrite the training metrics of our final model. Therefore, we pause autologging for the time of cross-validation.

In [9]:
from sklearn.metrics import root_mean_squared_error, mean_absolute_error, r2_score


def cross_validate_without_autolog(pipeline: Pipeline, X, y) -> np.ndarray:
    mlflow.sklearn.autolog(disable=True)
    try:
        return cross_val_score(pipeline, X, y, cv=5, scoring="r2")
    finally:
        mlflow.sklearn.autolog(**AUTOLOG_KWARGS)


def fit_sklearn_models(models, df_train, df_test, y_train, y_test):
    results = {}

    for model_name, model in models:
        pipeline = make_pipeline(model)

        # start MLflow run - a unit grouping logs from different model runs
        # everything within this context manager will get logged as a run
        with mlflow.start_run(run_name=model_name):
            cv_scores = cross_validate_without_autolog(pipeline, df_train, y_train)

            pipeline.fit(df_train, y_train)
            y_pred = pipeline.predict(df_test)

            metrics = {
                "cv_r2_mean": cv_scores.mean(),
                "cv_r2_std": cv_scores.std(),
                "test_rmse": root_mean_squared_error(y_test, y_pred),
                "test_mae": mean_absolute_error(y_test, y_pred),
                "test_r2": r2_score(y_test, y_pred),
            }
            # log additional custom metrics, in addition to autologging
            mlflow.log_metrics(metrics)

            results[model_name] = metrics

            print(f"\n{model_name}:")
            print(f"  CV R^2 (mean ± std): {metrics['cv_r2_mean']:.3f} ± {metrics['cv_r2_std']:.3f}")
            print(f"  Test RMSE: {metrics['test_rmse']:.2f}")
            print(f"  Test MAE: {metrics['test_mae']:.2f}")
            print(f"  Test R^2: {metrics['test_r2']:.3f}")

    return results

  1. What columns can be selected

  3. Select columns to compare a given metric between runs, e.g. test_mae
  4. Sort algorithms by cv_r2_mean to pick the best one

Note that we select the best model by cross-validation score, not by test score. If we picked the model with the best test score, the test set would become a part of model selection, and its score would no longer be an unbiased estimate of performance on new data.

Data preparation¶

Neural networks need a validation set for early stopping, i.e. stopping the training when the validation error stops improving. We hold out 20% of the training data for that purpose, while the 2008 data stays our test set.

We use log-prices as targets, as before. Additionally, we standardize them to zero mean and unit variance. Log-prices are around 12, and a freshly initialized network outputs values around 0, so without standardization, a large part of the training would be spent just on shifting the outputs.

class HousePriceNet(nn.Module):
    def __init__(self, input_dim: int, hidden_dim: int = 128, dropout_rate: float = 0.2):
        super().__init__()
        self.fc1 = nn.Linear(input_dim, hidden_dim)
        self.relu = nn.ReLU()
        self.dropout = nn.Dropout(dropout_rate)
        self.fc2 = nn.Linear(hidden_dim, 1)

    def forward(self, x):
        x = self.fc1(x)
        x = self.relu(x)
        x = self.dropout(x)
        x = self.fc2(x)
        return x

For a long time, plain MLPs were clearly worse than gradient boosting on tabular data. Recent tabular deep learning models have closed much of that gap. TabM (paper, ICLR 2025) is one of the strongest and simplest of them. It is an MLP that efficiently imitates an ensemble of k MLPs (by default k=32). Most weights are shared between submodels, so it costs only a bit more than a single MLP. A few things to note:

  • output has shape (batch, k, 1) - one prediction per submodel
  • during training, each submodel gets its own loss, and we minimize their mean, not the loss of the mean prediction
  • during inference, the final prediction is the mean of the submodels' predictions

To use both models with the same training code, we treat the MLP as an "ensemble" with k=1.

def create_model(config: dict, n_features: int) -> nn.Module:
    if config["model"] == "mlp":
        return HousePriceNet(
            input_dim=n_features,
            hidden_dim=config["d_block"],
            dropout_rate=config["dropout"],
        )
    elif config["model"] == "tabm":
        return TabM.make(
            n_num_features=n_features,
            d_out=1,
            n_blocks=config["n_blocks"],
            d_block=config["d_block"],
            dropout=config["dropout"],
        )
    raise ValueError(f"Unknown model: {config['model']}")

Training with manual logging¶

The trainer logs training and validation losses for each epoch, which shows the learning curves in the MLflow UI. It also implements early stopping: the training stops when the validation RMSE has not improved for patience epochs, and the weights from the best epoch are restored.

In [29]:
class PyTorchTrainer:
    def __init__(self, config: dict):
        self.config = config

    @staticmethod
    def predict(model: nn.Module, X: torch.Tensor) -> torch.Tensor:
        # shape (batch, k): MLP has k=1, TabM has k submodels
        return model(X).reshape(len(X), -1)

    def train_epoch(
        self, model: nn.Module, loader: DataLoader, optimizer: torch.optim.Optimizer
    ) -> float:
        model.train()
        total_loss = 0.0

        for X_batch, y_batch in loader:
            optimizer.zero_grad()
            y_pred = self.predict(model, X_batch)
            # mean of submodels' losses, not loss of the mean prediction
            loss = nn.functional.mse_loss(y_pred, y_batch.expand_as(y_pred))
            loss.backward()
            optimizer.step()
            total_loss += loss.item() * len(X_batch)

        return total_loss / len(loader.dataset)

    @torch.no_grad()
    def evaluate(
        self, model: nn.Module, X: torch.Tensor, y: torch.Tensor
    ) -> dict[str, float]:
        model.eval()
        y_pred = self.predict(model, X).mean(dim=1, keepdim=True)

        # revert standardization and logarithm to compute errors in dollars
        y_pred_dollars = np.expm1(y_pred.numpy().ravel() * y_log_std + y_log_mean)
        y_true_dollars = np.expm1(y.numpy().ravel() * y_log_std + y_log_mean)

        return {
            "loss": nn.functional.mse_loss(y_pred, y).item(),
            "rmse": root_mean_squared_error(y_true_dollars, y_pred_dollars),
            "mae": mean_absolute_error(y_true_dollars, y_pred_dollars),
            "r2": r2_score(y_true_dollars, y_pred_dollars),
        }

    def fit(
        self,
        train_data: tuple[torch.Tensor, torch.Tensor],
        val_data: tuple[torch.Tensor, torch.Tensor],
    ) -> tuple[nn.Module, dict[str, float]]:
        torch.manual_seed(self.config["random_seed"])

        X_train, y_train = train_data
        model = create_model(self.config, n_features=X_train.shape[1])
        optimizer = torch.optim.AdamW(
            model.parameters(),
            lr=self.config["learning_rate"],
            weight_decay=self.config["weight_decay"],
        )
        loader = DataLoader(
            TensorDataset(X_train, y_train),
            batch_size=self.config["batch_size"],
            shuffle=True,
        )

        best_metrics, best_state, best_epoch = None, None, 0
        for epoch in range(self.config["max_epochs"]):
            train_loss = self.train_epoch(model, loader, optimizer)
            val_metrics = self.evaluate(model, *val_data)

            # manually log metric values, with the epoch as the step
            mlflow.log_metrics(
                {
                    "train_loss": train_loss,
                    "val_loss": val_metrics["loss"],
                    "val_rmse": val_metrics["rmse"],
                },
                step=epoch,
            )

            if best_metrics is None or val_metrics["rmse"] < best_metrics["rmse"]:
                best_metrics, best_epoch = val_metrics, epoch
                best_state = copy.deepcopy(model.state_dict())
            elif epoch - best_epoch >= self.config["patience"]:
                break

        model.load_state_dict(best_state)
        mlflow.log_metric("best_epoch", best_epoch)
        mlflow.log_metrics({f"best_val_{name}": value for name, value in best_metrics.items()})

        return model, best_metrics

Hyperparameter optimization with Optuna¶

Choosing hyperparameters by hand quickly becomes tedious and does not scale. Optuna automates this: we define an objective function, which trains a model with hyperparameters suggested by Optuna and returns the validation error, and Optuna searches for the best values. By default, it uses the Tree-structured Parzen Estimator (TPE) algorithm, which focuses on promising regions of the search space based on previous trials.

Each Optuna trial is logged as a nested run, a child of the run representing the whole study. The MLflow UI groups child runs under their parent, so a whole study stays readable even with dozens of trials. Note that the objective uses only the validation set - the test set is not used for any decisions. We also enqueue our current configuration as the first trial, so the search starts from a known baseline and can only improve on it.

Model Registry¶

So far, models are logged in runs, and to use one, we would need to know its ID. The MLflow Model Registry is a central catalog of models intended for use. A registered model has a name, e.g. ames-price, and consists of numbered versions, each pointing to a logged model. Versions can be marked with aliases, e.g. champion for the production model and challenger for a candidate. Applications load models by alias, e.g. models:/ames-price@champion. Promoting a new model just moves the alias, without any change in the application code. Aliases replaced the deprecated "Staging" and "Production" stages from MLflow 2.

We register the scikit-learn pipelines, since they include preprocessing and accept raw data. The logged PyTorch networks expect already preprocessed features and return standardized log-prices, so they cannot be used on their own by an application.

Let's find the best scikit-learn run by cross-validation score. Since MLflow 3, a logged model has its own ID and URI (models:/<model_id>), independent of the run, so we look up the model logged by that run and register it:
